`50` 个 AI agent 框架的公开恢复记录被翻了个底朝天：`128` 条真实使用报告里，完全恢复的只有 `19` 条——checkpoint 恢复 `27` 条报告只成 `1` 次，回滚 `15` 条也只成 `1` 次。

论文题目直译是「被演练过，很少被恢复」。它审的对象不是模型能力，是 agent 基础设施的善后能力：编码 agent 删错文件、长跑任务中途崩了，用户能抓的稻草无非 checkpoint 续跑、撤销、回滚、读日志。研究运行时（runtime）承诺更强的 saga 补偿、事务回滚。这篇问的是：公开证据显示这些真管用吗？

## 一半是覆盖率幻觉

普查盘子：`12` 个常驻 agent 运行时、`26` 个编码 agent harness——名单里有 Claude Code、Aider、OpenHands、gemini-cli、kilocode 这些日常工具——外加 `12` 个研究运行时，共 `50` 个项目，按八种恢复机制从「查无」到「真实运行中用过」逐级打分。

单看这一层，行业成绩漂亮：`11/12` 的运行时、`25/26` 的 harness 至少有一条真实使用报告。恢复机制不是纸面功能，是真有人用过。

## 另一半是结局塌方

把 `128` 条使用报告的结局摊开：完全恢复 `19` 条，部分恢复 `54` 条，失败 `45` 条。「被演练过」和「恢复得了」是两回事。被用得最多的两种机制最难看：checkpoint/恢复在 `27` 条报告里只成功 `1` 次；回滚在 `15` 条里也只成 `1` 次——要么恢复点根本不存在，要么恢复回来状态还是坏的。

研究运行时走了另一个极端：补偿、回滚这些强保证在 benchmark 上评估得漂漂亮亮，实际运行中零报告；而「外部效应补偿」——把已经打出去的支付、已经发出去的消息对冲掉——这个它们的核心卖点，`26` 个 harness 一个都没提供。agent 圈外部的动作，目前没有任何主流工具打算帮你撤回。

## 谁做的，怎么做的，边界在哪

作者 Kaviru Hapuarachchi 是斯里兰卡科伦坡大学计算系的学生，独立完成，预印本未同行评审——但方法下了血本：编码协议在收数据前冻结，两轮盲编加仲裁，全部证据对归档源复核，复现包挂在 zenodo 上可下载。

三条边界必须带着读。第一，这是公开记录计数，不是失败率：作者在局限一节写明成功恢复大概率被漏报，issue tracker 天然只收藏失败。第二，七个评级最高的 E4 系统里六个靠单一操作者自报，作者自己承认这是最弱一环。第三，`12/26/12` 的样本按「公开可得证据」筛出，闭源商用 agent 的恢复能力这篇没资格说短长。

## 值不值得读

值得，而且姿势值得抄。此前站内读过的《AI 审查员抓不住研究内鬼》审的是别人代码里的破坏，这篇审的是全行业自己张贴的恢复证据——两篇合起来是一个趋势：审计的门槛不在实验室资源，在一套冻结的方法。一个本科生拿着协议和归档源，就给整个 agent 基础设施行业做了一次全员体检；体检结论是人人带着创可贴，没人带手术包。如果你的产品把「支持回滚」写进了卖点，这篇提醒你：先数一数它有过几次真的回滚成功。
