## 先还一笔旧账

本文首版（`2026-06-29`）有三处要撤：其一，「基准测试显示 PI 架构比 ReAct 提升 40%-50%」——无源，与谱系篇撤掉的 47% 属同一批伪证；其二，「某内部知识库系统成功率 58% 升至 87%」的实测案例——查无此事；其三，示例代码里的 `pip install mcp-sdk` 与 `PiPlanner` 类——`mcp-sdk` 这个包名在 PyPI 上并不存在（官方 SDK 的导入名是 `mcp`），`PiPlanner` 则是凭空虚构的框架类，首版还把一条与主题无关的 arXiv 论文错标成「PI 架构研究」。本版把「MCP 与规划-执行编排怎么接线」这个真实存在的工程问题重讲一遍：接口是具体的，代码可以跑，数字一个不编。编排格局与协议家族在[《六种协议与四个框架：2026 Agent互联格局》]({{ site.baseurl }}/paradigm-radar-agent-mcp-ecosystem-2026/)已有全景，本篇只钻「MCP 这一层与三件套的那道接缝」。

## 接缝只有一个：工具清单进、结构化结果出

把 MCP 与规划-执行编排各自抽象到最小，接合面只剩两个数据流。入流：Planner 需要知道「现在有哪些工具可用」——MCP 的 `tools/list` 返回带 JSON Schema 的工具清单，这份清单就是规划器的动作空间，协议化之前每个框架要自己维护一份会过期的工具表，之后动作空间成了每次规划前的实时查询。出流：Executor 调 `tools/call`，拿回结构化结果（内容块加 `isError` 标志），失败信息回流给修订器决定重试还是改计划。注意这两个数据流都不要求「MCP 与 PI 融合」这种宏大叙事——MCP 规范本体只有工具、资源、提示三种原语，它不知道也不关心调用方是不是先做了规划；所谓融合，实际是编排方把 MCP 当成动作空间的传输协议来用。首版把这点写成「两大范式的合体」，属于把接口调用拔高成了联姻。真正值得工程师注意的是接合面上的三个设计决定：清单什么时候取（每次规划前 vs 会话开始缓存，涉及工具漂移问题）、结果以多大粒度回传（全文进上下文还是摘要进计划状态，实战篇的隔离原则在此直接适用）、失败以什么形态流动（`isError` 只是布尔值，错误分类要编排方自己补——MCP 不管失败语义，这层空白正是 Monitor 归因职责的工作面）。

## 可以跑的代码走读

用官方 Python SDK（导入名 `mcp`）重写首版的示意代码，每一行都对应真实 API。会话与清单：`async with sse_client(url) as (r, w): async with ClientSession(r, w) as session: await session.initialize(); tools = (await session.list_tools()).tools`——拿到的是带 `name`、`description`、`inputSchema` 的对象列表，把每个工具的 Schema 序列化进 Planner 的提示词，动作空间就位。执行：`res = await session.call_tool(name, args)` 返回 `result.content`（文本块数组）与 `result.isError`；编排方的最小正确处置是 `isError` 为真时不抛异常、把错误文本连同工具名与入参指纹写进步骤记录，交回修订通道。与首版虚构代码的三处差异值得点名：包名（`mcp` 不是 `mcp-sdk`）、清单结构（真实返回是内容块数组不是裸字符串，解析层必须按类型分派）、以及传输假设（首版代码假定 `http://localhost:8000` 一个 URL 就够，真实世界里 stdio 与 SSE 两种传输的失败模式完全不同——stdio 的服务器进程崩了要在编排层做进程级重启，SSE 的断线重连则是会话层的事，这两种恢复路径都没法指望 MCP 自己完成）。二十行真代码胜过两百行伪代码的地方在于：每一行出错时你都能在文档里找到对应的段落，而虚构 API 的报错只会把你引向一个不存在的搜索结果页。

## 与原生 function calling 对照：MCP 到底多给了什么

诚实的对照要从不利于协议的问法开始：模型厂商的原生函数调用早已把「工具带 Schema、模型选工具、结果回上下文」在自家 SDK 内标准化了，一个只碰单一厂商栈的团队会觉得 MCP 是多余的一层。差值在乘积上：函数调用解决「一个客户端接 N 个工具」，MCP 解决「M 个客户端接 N 个工具」——服务器一次编写，Claude、OpenAI 系产品与任意兼容宿主皆可用，工具作者的分发问题从 M×N 份胶水降为 N 个服务器。第二个差值常被忽略：生命周期归属。函数调用的执行发生在你的进程里，工具的崩溃、并发、资源占用全是你进程的事；MCP 服务器是独立进程（或远程服务），编排层获得进程级隔离与重启单元，代价是上文说过的两种传输各有恢复路径。第三，也是规范文本才看得到的：roots 与 sampling 这类治理原语在函数调用里根本没有对应物——宿主边界声明与反向生成授权，是「工具住在别人家」之后才出现的问题。三项差值合起来，选型的正确问法从「MCP 比 function calling 强多少」变成「我的工具生态有没有跨客户端分发需求」：有，MCP 是现成的解；没有，多一层进程与协议的开销确实需要自证值得。

## 另外四成协议面：resources、prompts、sampling、roots

首版只讲了 tools，等于把规范读了三分之一。resources 原语把「可读的上下文源」与「可调的操作」分开建模——数据库里的一张表适合被引用进计划而不是被执行，编排层的正确用法是在 Planner 的上下文装配阶段按 URI 选择性拉取，与实战篇的隔离原则严丝合缝：资源进上下文的粒度决策与工具结果同构。prompts 原语是服务器随工具一起发布的指令模板，值得与[《一份技能文件写一次，所有客户端都能跑》]({{ site.baseurl }}/paradigm-radar-skill-md-standard/)对照读：两者都在解决「把领域 know-how 随能力一起交付」，分工是 MCP 模板活在服务器端随版本升级、SKILL.md 活在文件系统随仓库分发，一个 agent 完全可能同时吃两种来源的指令——届时谁的模板优先，规范没有答案，这是接缝上尚未显形的新坑。sampling 是规范里唯一的方向反转原语：服务器反过来请求宿主授权一次模型生成——工具「借用」你的模型意味着动作空间第一次双向化，编排层要把它当作与 `tools/call` 同级的权限事件处理，默认拒绝、逐条放行。roots 则把宿主的文件系统边界声明给服务器，方向是治理而非能力——读到这四个原语再回头看「MCP 只是工具总线」的说法，就会发现规范作者早就把治理面写进了原语名单，只是大多数教程只教 `tools/call` 一个函数。

## 漂移问题：协议解决不了的那一半

MCP 把「工具长什么样」标准化了，「工具变了怎么办」留给每个人自己。工具漂移有三种速度，各配一种拦截。慢漂移（服务器升级改了 Schema）：把 `tools/list` 的清单哈希进计划版本号，规划与执行各查一次，不一致即触发重规划——这比等到调用报参数错误再恢复便宜一个数量级。快漂移（两次调用之间世界变了，比如 OAuth 令牌过期）：MCP 的认证在宿主层处理，编排层要做的不是防漂移而是给认证类失败单独开快速通道——令牌刷新的重试不该消耗 replan 预算。静默漂移（工具还在、语义变了，返回结构一致但含义换了）：这是唯一没有协议级解法的漂移，只能靠输出端的断言网兜住——实战篇的「完成条件机器可判」在这里从评测方法变成运行时防线——顺带一句，静默漂移是唯一能骗过离线评测基准的漂移，换过服务器实现之后，你的评测基线也要跟着重基线，否则测的是旧工具的鬼魂。三种漂移合起来给出一句实用结论：MCP 消除的是集成的重复劳动，没有消除集成的维护责任，把「接上 MCP」当成「工具层从此免维护」的团队，第一个版本升级会收回这句错觉的全部学费。生态侧的现实校验放在结尾：参考服务器仓库 modelcontextprotocol/servers 实测（`2026-11-16`）`92,025` 星、`11-12` 仍有提交，官方参考实现的维护热度不必担心；要担心的是社区服务器的质量长尾——协议只保证握手正确，不保证语义诚实，同一个「文件系统服务器」在不同实现手里的读权限宽严能差出一个量级，接入评审清单里「拿别人的服务器跑一遍越界读写测试」应当是固定项。协议选型与安全边界（工具接入面变宽后的权限问题）在互联格局篇与[《Agent 权限清单要住进哪个载体》]({{ site.baseurl }}/paradigm-radar-agent-permission-artifact/)各有展开——MCP 是所有管道里最宽且最不设防的那根，本篇的接缝越标准化，那句话越要贴在工位上。

## 落地 runbook：接一台服务器的完整七步

把全篇折成一份可抄的接入序列。一步定传输：本机信任选 stdio，跨机或多租户选带认证的 SSE/HTTP，这一步决定后文全部故障模式。二步钉版本：客户端记录并校验服务器报的协议协商版本，升级走灰度。三步取清单：`tools/list` 后连工具描述的哈希一起入库存档，形成漂移基线。四步注册校验器：为每个工具的 `inputSchema` 生成本地断言，调用前拦截不合规入参——把服务器的解析失败变成自己的可归因失败。五步装配计划上下文：工具 Schema 全文进 Planner，资源按 URI 拉摘要进上下文，二者都走实战篇的隔离通道。六步建失败通道：`isError` 与异常分开路由（语义失败进修订队列、传输失败进重试队列），错误文本连工具名入指纹库供归因。七步设巡检：定时重取清单比对哈希、抽样跑一条只读工具做端到端健康检查——漂移的三种速度里最快的那种，只有巡检能在调用之前抓住。七步全部做完，一个 MCP 服务器才算真正「接入」；只做前三步的团队，规范文档里那些兼容性条款会在没人盯的夜里默默失效——集成事故从来不开会通知。

## 边界与观察点

两条边界。其一，本篇只覆盖工具层与编排层的接缝，agent 间调用的 MCP↔A2A 桥接（远端 agent 在本地伪装成一个工具）是互联格局篇的地盘，那里有「任务生命周期与工具调用的短平快节奏不匹配」的具体困难。其二，MCP 规范的多厂商治理仍在演进（规范以日期版本化发布，服务器与客户端靠协商兼容），把它写进长期架构前先读一遍互联格局篇的治理观察。观察信号两条：`tools/list` 会不会长出清单版本或变更通知原语——若出现，上文慢漂移的自建哈希校验就能退役，这是判断规范是否开始接管运维语义的最小组件；以及错误结构会不会从布尔 `isError` 演进为类型化错误码——Monitor 的归因职责在协议层拿到现成输入的那天，编排框架的失败分类学才算有了公共底座。两条都中格，工具层与编排层的接缝就从「自己焊」进入「按图纸装」的时代；都落空，本文的 runbook 请继续贴满工位。
